# Phase 1 — Interviewer answers
# #	Your clarification	Interviewer decision
# 1	Skip login?	Yes. Authentication and authorization are out of scope.
# 2	Can clients schedule tasks?	Yes. Clients can submit tasks, inspect their status, and cancel pending tasks.
# 3	One-time or repeating?	Both. Support one-time execution and fixed-interval recurring execution.
# 4	Does the client pass a thread?	No. The client provides a task definition or executable action and its schedule. The scheduler owns thread allocation and worker execution.
# 5	Can the same task be scheduled twice?	Yes. Two submissions of the same action create two independent task instances. Each receives a unique task ID.
# 6	What happens on failure?	Track failure and support configurable retries. Acknowledgment of successful execution is required.
# 7	Task validation?	Yes. Validate scheduling parameters, priority, and required task information.
# 8	Rate limiting?	Out of scope.
# 9	Task execution duration?	Yes. Tasks can take different amounts of time. Workers remain occupied until execution finishes.
# 10	Task priority?	Yes. Support P0, P1, and P2, with P0 highest.

# Important clarification about priority
# Your scenario is valid.

# Suppose two workers are available, and at second 10 we have:
# Task	Scheduled time	Priority	Status
# T1	8	P1	Waiting
# T2	9	P1	Waiting
# T3	10	P0	Waiting
# T4	10	P0	Waiting

# At second 10, T3 and T4 should be dispatched before T1 and T2, assuming all are eligible and no task has already started.

# However, if T1 is already running, we do not interrupt it when T3 arrives.

# V1 uses non-preemptive priority scheduling.

# This distinction matters because task eligibility, task priority, and worker availability are separate concepts.
# Requirements you missed
# Core — Worker capacity

# The scheduler has a configurable fixed-size worker pool. Multiple tasks can execute concurrently, but no more than the worker count.


# Core — Task lifecycle

# Track SCHEDULED, RUNNING, COMPLETED, FAILED, and CANCELLED. Retries must also be represented consistently.


# Core — Retry policy

# A task may retry after failure, with configurable maximum attempts and a fixed retry delay. Once attempts are exhausted, it becomes terminally failed.


# Core — Ordering

# Among eligible tasks with equal priority, dispatch the earliest scheduled task first. Break remaining ties by submission order.


# Extension — Durability and crash recovery

# Not required in V1. Assume a single JVM with in-memory state. We can discuss process crashes, duplicate execution, and persistence afterward.
