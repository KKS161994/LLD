## Corrected Phase 1 — Monitoring & Alerting System

### 1. Actors

- Service owner — registers services and configures alert rules.
- Application — submits metric samples.
- Notification provider — delivers notifications through email or SMS.

### 2. Actions

Service owner: Register application, configure/update rules, configure notification recipients.

Application: Submit batches of metric samples containing `serviceId`, `metricName`, `value`, and `timestamp`.

System: Validate metrics, evaluate matching rules, detect state transitions, generate alert events, and request notification delivery.

Notification provider: Attempt delivery and report success or failure.

### 3. Flows

Normal alert flow:

`Register service → Configure rule → Receive metric → Validate → Evaluate → HEALTHY to FIRING → Generate alert → Notify`

Recovery flow:

`Receive healthy metric → Evaluate → FIRING to HEALTHY → Allow future alert`

Repeated violation:

`FIRING → Another violating metric → Remain FIRING → No new alert`

### 4. States

| Resource              | States                            | Comment                        |
| --------------------- | --------------------------------- | ------------------------------ |
| Application           | REGISTERED, DISABLED              | Only if disabling is supported |
| Alert rule evaluation | HEALTHY, FIRING                   | Correct owner of alert state   |
| Notification          | PENDING, DELIVERED, FAILED        | If tracking delivery           |
| Metric sample         | No persistent lifecycle necessary | Evaluated synchronously        |

### 5. Constraints & Invariants

1. Each registered service must have a unique identity.
2. Metrics must belong to a valid, enabled service.
3. Each rule must have valid configuration, including threshold, operator, and recipients.
4. Each rule independently maintains HEALTHY/FIRING state.
5. At most one alert event is generated for each transition into FIRING.
6. Continued violations must not generate additional alert events until recovery.
7. Concurrent evaluations must preserve these invariants.

Important: We allow multiple rules for the same service and metric, so two rules can legitimately generate two alerts.

### 6. Failures

| Scenario                      | Expected behavior                                                         |
| ----------------------------- | ------------------------------------------------------------------------- |
| Invalid metric                | Reject with validation error                                              |
| Unknown service               | Reject with service-not-found error                                       |
| Disabled service              | Reject ingestion, if disabling is supported                               |
| Duplicate registration        | Reject or return existing registration, based on agreed API contract      |
| Concurrent violating metrics  | Generate only one firing event per rule transition                        |
| Notification delivery fails   | Record failure; no automatic retry under your proposed one-attempt policy |
| Out-of-order samples          | Clarify whether evaluation follows arrival order or event timestamps      |
| One invalid sample in a batch | Clarify whether the entire batch fails or only the invalid sample         |

### 7. Boundaries

For this mock, we have agreed on:

- Single JVM, in-memory implementation.
- Numeric metric samples.
- Latest received value evaluation, not rolling averages.
- Retain recent metrics for 10 minutes.
- Multiple rules per service and metric.
- Synchronous rule evaluation.
- No Kafka, distributed storage, or persistent analytics.
